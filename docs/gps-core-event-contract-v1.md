# GPS → Core: контракт предварительных событий (v1)

Статус: проект контракта для интеграции с чатом 2. Изменений в доменной модели Core нет.

## Правила
- GPS **не изменяет** подтверждённые интервалы работы, ставки, оплаты или ручные записи. Core сам управляет подтверждением.
- Все события GPS изначально `provisional`; `confirmed` допускается только после явного действия пользователя в Core.
- Сохранять локально на устройстве; никакой передачи координат на сервер. Не передавать точные координаты в Core, если достаточно objectId.
- Временные метки — Unix epoch milliseconds UTC (`timestampMs: Long > 0`). Для отображения Core использует локальный часовой пояс.
- `objectId` — неизменяемый ID существующего объекта (не имя/индекс списка). Если соответствие неуверенное, `null`, без автоматического создания объекта.
- `eventId` — устойчивый ID одного логического события, сохраняемый при рестарте, повторной доставке и экспорте/импорте. Core дедуплицирует по `eventId`.

## Формат события
| Поле | Тип | Требование |
|---|---|---|
| eventId | String | Обязателен, непустой, стабильный при повторной доставке |
| kind | enum | TRIP_START, TRIP_STOP, ARRIVAL, DEPARTURE, OBJECT_VISIT, GPS_GAP |
| timestampMs | Long | >0, время события, не время обработки |
| objectId | String? | Для привязанных к объекту событий; null для неизвестных |
| tripId | String? | Один ID для начала/окончания поездки |
| confidence | enum | LOW, MEDIUM, HIGH (не вероятность и не подтверждение) |
| confirmation | enum | PROVISIONAL, USER_CONFIRMED, USER_REJECTED |
| source | String | gps-v1 |
| evidenceStartMs / evidenceEndMs | Long? | Границы наблюдаемой доказательной базы; start <= end |

## Семантика
- `TRIP_START`: начало подтверждённого последовательностью координат движения, а не одиночным сигналом акселерометра.
- `TRIP_STOP`: остановка наблюдаемой поездки; не создаётся при старте службы в состоянии покоя и после неизвестного разрыва.
- `ARRIVAL` / `DEPARTURE`: устойчивое пересечение геозоны с dwell и допустимой точностью. Кратковременное пребывание на границе не подтверждает событие.
- `OBJECT_VISIT`: предложение о посещении объекта при достаточных свидетельствах; может ссылаться на прибытие и остановку.
- `GPS_GAP`: потеря непрерывности наблюдений, **не** доказательство окончания поездки или ухода с объекта.

## Повторная доставка и согласование
1. Производитель сохраняет событие и устойчивый `eventId` перед выдачей Core; повторная доставка не меняет ID.
2. Core делает upsert по `eventId`; не допускает второе начисление или второй интервал при повторной доставке.
3. Порядок доставки может отличаться от `timestampMs`; Core сортирует по времени, а при равном времени — по `eventId`.
4. События с `timestampMs <= 0`, неизвестным `kind`, противоречивыми границами или неизвестным объектом нельзя автоматически превращать в рабочие интервалы.
5. Перекрытие с ручной записью: ручная/подтверждённая запись приоритетнее GPS-подсказки. GPS не сокращает, не расширяет и не удаляет её. При пересечении Core показывает предложение для проверки.
6. Открытая поездка, GPS_GAP, ошибочная точка, смена источника GPS и рестарт службы — неполные свидетельства, требующие осторожной обработки без догадки о рабочем времени.
7. Отклонение пользователем сохраняется, чтобы повторная доставка того же `eventId` не показывала предложение снова.

## Границы интеграции
- Чат 1 предоставляет адаптер чтения GPS evidence/events и сохраняемые идентификаторы; текущие классы `GpsWorkActivityHints`, `GpsTripRules`, `GpsRecoveryRules` и `GpsShiftEstimate` — источники свидетельств, не API Core.
- Чат 2 реализует модель предложения/подтверждения и приоритет ручных интервалов в **своей** ветке. Никаких прямых изменений записей оплаты из GPS.
- Совместно согласовать сериализацию и миграцию существующих GPS-событий без потери данных до подключения интерфейса.

## Критерии приёмки интеграции
- Повторная доставка / рестарт не дублируют подсказки.
- Некорректные/потерянные GPS-данные не создают рабочее время.
- Ручные и подтверждённые интервалы и сумма оплаты остаются неизменными.
- События без ID объекта безопасно остаются неподтверждёнными.
- При отсутствии GPS Core продолжает ручной учёт.
